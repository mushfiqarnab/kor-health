# ADR 0009: Secure Local Unlock Material Boundary

## Status

Accepted.

## Date

2026-05-18

## Context

Slice 8 integrated local vault assembly with sealed root keys. It created one local sealed root_key record under K_local_unlock and one backup sealed root_key record under K_recovery_wrap.

Slice 9 defines the secure local boundary for protecting K_local_unlock.

K_local_unlock is not generated in this slice. It is not derived from a password. It is not backed by SQLite salt or iteration metadata. It is a random 32-byte local unlock capability key generated by the key-material layer and protected through a secure local secret boundary.

This slice creates a testable application policy and infrastructure port without importing Expo SecureStore directly.

## Decision

The system now has a Secure Local Unlock Material Boundary with two parts:

1. Application policy
2. Infrastructure secure local secret store port

The application policy validates and serializes K_local_unlock material.

The infrastructure boundary stores, loads, and deletes the serialized material through an injected secure local secret driver.

The concrete Expo SecureStore adapter is intentionally left for a future slice.

## Scope

This slice implements:

- local unlock material validation
- local unlock material serialization
- local unlock material deserialization
- explicit failure states for local unlock loading
- secure local secret driver interface
- secure local unlock store functions
- wrong-purpose key rejection
- malformed stored value rejection
- explicit locked state mapping
- best-effort key byte zeroing

This slice does not implement:

- Expo SecureStore adapter
- Secure Enclave generation
- Android Keystore direct integration
- SQLite
- WatermelonDB
- Supabase
- Shamir Secret Sharing
- recovery flow
- password KDFs
- Argon2
- PBKDF2
- UI prompts
- clinical metadata

## Local Unlock Material

The only accepted local unlock material has:

- keyScopeId
- keyVersion
- purpose: local_keyring
- rawKeyBytes: Uint8Array

The raw key material must be exactly 32 bytes.

The keyScopeId must be opaque and non-semantic.

The following purposes are rejected as local unlock material:

- keyring_backup
- payload_encryption
- blind_index
- caregiver_adherence
- emergency_card
- root_key

## Stored Representation

Local unlock material is serialized as:

local-unlock-v1:<base64url-canonical-json>

The encoded payload contains:

- schemaVersion
- materialType
- keyScopeId
- keyVersion
- purpose
- rawKeyBytesBase64Url

The stored value is intended for a secure local secret store, not SQLite, Supabase, logs, or ordinary app state.

## Lock State Model

Loading local unlock material returns one of these states:

- unlocked
- locked_missing
- locked_cancelled
- locked_unavailable
- locked_malformed
- locked_auth_changed

Driver failure mapping:

- missing stored value becomes locked_missing
- authentication cancellation becomes locked_cancelled
- authentication state change becomes locked_auth_changed
- driver unavailable becomes locked_unavailable
- unknown driver failure becomes locked_unavailable
- malformed stored value becomes locked_malformed

Failure states must not include raw key material or serialized local unlock values.

## Secure Local Secret Driver

The infrastructure boundary depends on this port:

- setItem(key, value)
- getItem(key)
- deleteItem(key)

The future Expo SecureStore adapter must implement this port.

Application logic must not import Expo SecureStore directly.

## Storage Key

The current storage key format is:

kor:v1:local-unlock:<patientId>:<keyringId>

The patientId and keyringId used here must be opaque internal identifiers. They must not contain NID, phone number, email, patient name, clinical category, or domain labels.

A future slice may replace this with a hash-derived opaque storage key if required.

## Metadata Leakage Policy

The following must not appear in serialized local unlock values or local unlock metadata:

- K_root
- K_master
- K_local_unlock
- K_recovery_wrap
- domain/general
- domain/mental
- mental
- mental-health
- psychiatric
- reproductive
- oncology
- HIV
- diabetes
- NID
- e-TIN
- phone
- email
- DOB

Raw key bytes are non-enumerable in LocalUnlockMaterial objects.

## Security Behavior

K_recovery_wrap must never be accepted as K_local_unlock.

Payload encryption keys must never be accepted as K_local_unlock.

Malformed stored values fail closed.

Wrong-length key material fails closed.

Wrong-purpose key material fails closed.

Authentication failures produce explicit locked states instead of exceptions containing sensitive material.

## Platform Note

The future Expo SecureStore adapter must treat platform behavior carefully.

SecureStore is a local secret boundary. It is not the encrypted medical database and it is not the whole vault.

Retrieved key bytes still exist in JavaScript memory temporarily, so cleanup is best-effort, not guaranteed physical zeroization.

## Consequences

Positive consequences:

- K_local_unlock now has a clear local protection boundary.
- Expo SecureStore remains behind an infrastructure port.
- Application logic remains testable in Node/Vitest.
- Unlock failures are explicit and safe.
- Wrong-purpose key confusion is blocked.
- No database, cloud, recovery, or UI concern is introduced prematurely.

Trade-offs:

- This slice still does not call real Expo SecureStore.
- This slice does not implement biometric prompts.
- This slice does not solve recovery if local unlock material is missing.
- JavaScript memory cleanup remains best-effort.
- Storage key identity must remain opaque.

## Next Technical Target

The next target is the Expo SecureStore Adapter Slice.

That future slice should implement SecureLocalSecretDriver using Expo SecureStore with authentication-gated access, while preserving the same policy and locked-state behavior defined here.
